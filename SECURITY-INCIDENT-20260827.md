## Дыра найдена (27.08.2026)

**CVE-2025-55182 «React2Shell»** — pre-auth RCE в протоколе React Server Components
(CVSS 10.0; downstream по Next.js — CVE-2025-66478). Один POST с подготовленным
сериализованным RSC-объектом десериализуется на сервере и выполняет код в Node.js.
Публичные разборы отмечают: эксплуатация с декабря 2025, надёжность близка к 100 %,
и **основная полезная нагрузка в дикой природе — как раз майнеры**.

parta5 подпадал: `next@15.3.2` + `react@19.2.6`. Патч своей линии — **15.3.6**
(полный список: 15.0.5, 15.1.9, 15.2.6, 15.3.6, 15.4.8, 15.5.7, 16.0.7;
для 13.3+/14.x — 14.2.35).

### Чем доказано

В коде приложения нет ни одного `"use server"` и ни одного вызова shell
(`child_process`/`exec`/`spawn` — только `RegExp.exec` в `lib/brand.ts`).
Команды исполнял фреймворк, не наш код.

Access-лог `proxy-nginx` (`/var/lib/docker/containers/2b265de9…-json.log`,
ведётся с 09.07.2026) содержит ровно **74 запроса** `POST / HTTP/1.1` → **303**
с телом ≈4,5 КБ (RSC-ответ с редиректом). Все — с двух соседних адресов
ColoCrossing: `23.95.96.140` (3) и `23.94.216.234` (71), с рандомизированным
User-Agent на каждый запрос. Дроппер `172.245.88.160` — тот же провайдер.

Каждой попытке `sh` внутри контейнера соответствует такой POST **в ту же секунду**:

| POST / → 303 (UTC)  | `sh: curl: not found` в stderr |
| ------------------- | ------------------------------ |
| 2026-08-12T04:45:15 | 04:45:15.264                   |
| 2026-08-13T10:04:57 | 10:04:57.137                   |
| 2026-08-14T18:29:30 | 18:29:29.665                   |
| 2026-08-18T00:22:54 | 00:22:54.593                   |
| 2026-08-27T07:15:14 | 07:15:14.846                   |

**Первое успешное срабатывание — 04.08.2026 07:11:08 UTC** (10:11 MSK) с `23.95.96.140`,
то есть на два дня раньше, чем считалось. Запрос, предшествовавший появлению
`/tmp/XXPBIJCl`, — **06.08.2026 16:31:37 UTC** (19:31 MSK), тот же адрес.
Дальше — `23.94.216.234` с 11.08 и ритмом **раз в ~7 ч 05 мин** до самой остановки.
Это не наш cron внутри контейнера, а внешний цикл сканера: заражение возобновлялось
после каждого перезапуска.

Тела запросов в `combined`-формате не сохраняются — сам payload не восстановить.
Выборки: `/root/incident-20260827/post-root-303.log` и `attacker-23.94.216.234.log` на sel1.

## Как быстро проверить, что заражения нет

```bash
# посторонние процессы (norm: только next-server / node)
docker top parta5-web

# файлы-маркеры в /tmp
docker exec parta5-web ls -la /tmp

# исходящие соединения контейнера (norm: только db/redis/minio внутри 172.x)
nsenter -t $(docker inspect parta5-web --format '{{.State.Pid}}') -n ss -tnp
```

Тревожный признак — процесс со случайным именем из букв и высоким CPU,
исходящее соединение на внешний IP с нестандартным портом (33333, 3333, 14444 и т.п.).
