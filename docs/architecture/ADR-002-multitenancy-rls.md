# ADR-002: Мульти-тенантность через PostgreSQL Row Level Security

**Статус:** принято  
**Дата:** 2026-05-26

## Контекст

LMS обслуживает несколько школ (тенантов). Нужно гарантировать изоляцию данных:

- Ошибка в приложении не должна позволить школе А видеть данные школы Б
- Подходит для self-host (одна инстанция = одна школа) и SaaS (несколько школ)

## Варианты

| Подход                                     | Изоляция | Сложность                    | Подходит для self-host |
| ------------------------------------------ | -------- | ---------------------------- | ---------------------- |
| Отдельные схемы PostgreSQL                 | ✓✓       | Высокая (N схем, N connpool) | Нет (overhead)         |
| Row-level `school_id` + application filter | ✓        | Низкая                       | Да                     |
| **RLS (выбрано)**                          | ✓✓       | Средняя                      | Да                     |

## Решение

Каждая таблица с тенант-данными имеет `schoolId UUID NOT NULL`.  
PostgreSQL RLS включён с `FORCE ROW LEVEL SECURITY` (блокирует и table owner).  
Политика: `USING ("schoolId" = current_setting('app.current_school_id', true)::uuid)`.  
Prisma middleware устанавливает сессионный параметр через `SELECT set_config(...)` в начале каждой транзакции (`withTenant()` хелпер).

## Последствия

- Даже баг в tRPC не позволит cross-tenant утечку (защита на уровне БД)
- Миграции RLS применяются отдельным шагом после `prisma migrate`
- Для dev/test нужно явно вызывать `withTenant()` или использовать superuser (обходит FORCE RLS)
- `current_setting` возвращает пустую строку если параметр не задан — это не UUID, cast упадёт. Поэтому `true` (missing_ok) предотвращает ошибку, но запрос вернёт 0 строк — безопасное поведение по умолчанию

## Откат

RLS можно отключить командой `ALTER TABLE ... DISABLE ROW LEVEL SECURITY` без изменения схемы, с fallback на application-level фильтрацию.
