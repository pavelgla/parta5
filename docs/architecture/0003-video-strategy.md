# ADR-003 — Video Strategy: Self-Hosted HLS + Universal Embed

**Status:** Accepted  
**Date:** 2026-05-26  
**Deciders:** Paul Gladyshev

---

## Context

Парта5 позиционируется как self-host LMS, где школа запускает `docker compose up` и работает автономно — без обязательной зависимости от внешних SaaS. Видео — ключевой тип контента для учителей. Нужно решить, как доставлять видео ученикам так, чтобы:

1. Персональные данные (записи лекций учителей, видеоматериалы) оставались внутри контура школы.
2. Не требовалось платить за внешний видеохостинг.
3. Работало на медленных школьных сетях (адаптивный битрейт).
4. Учителя, уже использующие YouTube/RuTube/VK, могли встраивать видео оттуда без перезалива.

---

## Decision

**Self-hosted HLS как дефолт + универсальный embed как опция.**

- **Self-hosted HLS:** Учитель загружает mp4/webm → S3 (MinIO локально, Yandex Object Storage / VK Cloud в облаке) → BullMQ-воркер с FFmpeg транскодирует в HLS (360p / 720p / 1080p, `master.m3u8` + сегменты) → результат обратно в S3 → клиент стримит через HLS.js с адаптивным битрейтом.
- **Универсальный embed:** Учитель вставляет URL — система автоматически детектирует провайдера (YouTube, RuTube, VK Видео, Kinescope, Vimeo, Boomstream, Дзен) и рендерит iframe. Никаких API-запросов — только парсинг URL.
- **Адаптеры коммерческих SaaS** (Kinescope, Boomstream, PlatformCraft, Yandex Cloud Stream) — в ядро Phase 1 не включаются. Закладывается только `VideoAdapter` интерфейс; коммерческие реализации — в Phase 4+ как опциональные модули.

---

## Alternatives Considered

**1. Только embed (без self-hosted)**  
Простейшая реализация: учитель всегда указывает URL, мы показываем iframe.  
Отклонено: нарушает философию self-host и 152-ФЗ (данные у Google/других); школы, не желающие зависеть от внешних сервисов, теряют возможность нормально работать.

**2. PeerTube**  
Open-source видеоплатформа с ActivityPub. Можно поднять рядом с Парта5 и интегрировать через API.  
Отклонено: дополнительный сервис с высоким порогом настройки; избыточен для школьного use-case; требует отдельного домена и администрирования; лицензия AGPL конфликтует с ядром Парта5 (MPL 2.0).

**3. MediaCMS**  
Open-source видеохостинг на Django. Аналогично PeerTube.  
Отклонено: те же проблемы — отдельный стек, Python + Django vs Node.js монолит, чужой admin-интерфейс, который придётся объяснять пользователям.

**4. Адаптеры коммерческих SaaS в ядре**  
Кинескоп, Boomstream и др. дают CDN, DRM, аналитику «из коробки».  
Отклонено для Phase 1: вводит обязательную зависимость от платного сервиса; API-ключи нужны при первом запуске; не все школы имеют бюджет. Правильный путь — опциональные платные модули в Phase 4+.

---

## Consequences

**Плюсы:**

- Нулевая зависимость от внешних сервисов для базового сценария.
- Данные школы не покидают её инфраструктуру.
- Адаптивный битрейт (HLS) — работает на медленном 3G.
- Гибкость: школа сама выбирает, где хранить S3 (MinIO / Yandex / VK Cloud).
- Embed как «запасной выход» для учителей, уже загрузивших контент на YouTube.

**Минусы:**

- Нагрузка CPU при транскодинге. Для школы с 10–50 видео в неделю — приемлемо на одном VPS. При росте — вынести `worker` на отдельную машину.
- Первое воспроизведение HLS добавляет 1–2 с на загрузку плейлиста (playlist fetch + сегмент). Приемлемо.
- FFmpeg нужен в production Docker-образе → +100 MB к размеру образа worker.
- Нет CDN для HLS-сегментов в Phase 1. При >100 одновременных зрителей потребуется CDN или отдельный S3 с публичным доступом. Добавляется в Phase 3+.
