# ADR-004: Модель данных оценивания (квиз-движок)

**Статус:** принято
**Дата:** 2026-07

## Контекст

Этап B суперплана (см. `docs/SUPERPLAN.md`, «Этап B — Квиз-движок MVP») требует модели данных для банка вопросов, тестов (квизов) и попыток их прохождения. Ключевой драйвер — пилотная миграция Профспецресурса (PSR): в Moodle 5.0.6 у них накоплено 62 942 вопроса, из которых **62 940 — multichoice**. Остальные типы (essay, numerical, matching, cloze и т.д.) в реальных данных пилота практически не встречаются.

Нужно решить:

- Как хранить содержимое вопроса, чтобы поддерживать разные типы (multichoice/truefalse/shortanswer сейчас, остальные — после пилота) без миграции схемы на каждый новый тип.
- Как гарантировать, что правка вопроса учителем не ломает уже сданные (или начатые) попытки учеников.
- Где выполняется автоматическая оценка ответа — на клиенте или на сервере.
- Как закрывать попытки, у которых истёк таймер, если ученик не нажал «сдать».
- Мультитенантность (`schoolId` + RLS) — обязательна для всех новых таблиц по [ADR-002](ADR-002-multitenancy-rls.md).

## Решение

### Модели (Prisma)

| Модель         | Назначение                                                                                            |
| -------------- | ----------------------------------------------------------------------------------------------------- |
| `QuestionBank` | Категории вопросов, дерево через self-relation `parentId` (аналог категорий Moodle)                   |
| `Question`     | Один вопрос: `type` (enum), `data` (`Json`, содержимое по типу), `version` (Int, версионирование)     |
| `Quiz`         | Настройки теста: `timeLimitSeconds`, `maxAttempts`, `passingScore`, `shuffleQuestions`                |
| `QuizQuestion` | m:n Quiz↔Question, с `order` и `points` (баллы вопроса в контексте конкретного теста)                 |
| `QuizAttempt`  | Попытка прохождения: `status` (`IN_PROGRESS` / `SUBMITTED` / `EXPIRED`), `questionsSnapshot` (`Json`) |
| `QuizResponse` | Ответ ученика на один вопрос в рамках попытки: `answer` (`Json`), `isCorrect`, `points`               |

Все модели содержат `schoolId UUID NOT NULL` и попадают под RLS-политику `school_isolation`, по образцу [ADR-002](ADR-002-multitenancy-rls.md) — без исключений, с первого коммита пакета.

### Содержимое вопроса — JSON + zod, не колонки на подтип

`Question.data` — это `Json`-колонка, содержимое которой валидируется zod-схемами из пакета `@parta5/quiz` (по одной схеме на `type`), а не набором специфичных для каждого подтипа SQL-колонок или отдельных таблиц.

Обоснование:

- Гибкость: новый тип вопроса — это новая zod-схема в пакете, без миграции БД.
- Единая точка валидации: одна и та же схема используется и на клиенте (форма редактирования вопроса), и на сервере (tRPC-процедура, импортер) — исключает рассинхрон правил.
- Простой импорт из Moodle XML (Этап C): парсер маппит XML прямо в JSON-структуру нужного типа, без построения сложных JOIN-запросов на insert.

### MVP-типы вопросов

На старте поддерживаются три типа, покрывающие данные пилота:

- **MULTICHOICE** — один или несколько правильных ответов (`single`/`multi`), перемешивание вариантов (`shuffle`), обратная связь (`feedback`) на каждый вариант.
- **TRUEFALSE** — частный случай выбора из двух вариантов.
- **SHORTANSWER** — список принимаемых ответов (текстовых шаблонов), сравнение case-insensitive.

Обоснование цифрами: в целевой миграции (Профспецресурс, Moodle 5.0.6) 62 940 из 62 942 вопросов банка — multichoice. Остальные типы Moodle (matching, essay, numerical, cloze и др.) откладываются на после пилота — расширение `@parta5/quiz` новой zod-схемой не требует изменения Prisma-схемы.

### Снапшот вопросов в попытке

При старте `QuizAttempt` (`status = IN_PROGRESS`) текущие данные всех вопросов теста копируются в `questionsSnapshot` (`Json`). Последующая правка вопроса учителем (новый `Question.version`) не влияет на уже начатые или сданные попытки — они оценивались и отображаются по снапшоту на момент старта. Пересдача (новая попытка, если позволяет `maxAttempts`) идёт по актуальной версии вопроса.

### Оценивание — чистые функции, только на сервере

Оценка выполняется чистыми функциями `grade(question, answer) -> { isCorrect, points }` в пакете `@parta5/quiz`. Эти функции вызываются исключительно сервером (tRPC-процедура `attempt.submit`) на основе `questionsSnapshot` попытки. На клиенте никакой логики выставления оценки нет — иначе ученик мог бы получить правильный ответ или баллы через инструменты разработчика браузера.

### Попытки с дедлайном и просрочка

Для попытки с ограничением по времени вычисляется `expiresAt = startedAt + timeLimitSeconds`. Фоновая cron-задача в `apps/worker` (`expire-attempts`, задача B7 суперплана) периодически находит попытки в статусе `IN_PROGRESS` с `expiresAt < now()`, переводит их в `EXPIRED` и выставляет оценку по уже сохранённым `QuizResponse` — ответы, которые ученик не успел дать, засчитываются как отсутствующие/неверные.

## Рассмотренные альтернативы

| Альтернатива                                                                                  | Причина отклонения                                                                                                                                      |
| --------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Отдельная SQL-таблица на каждый тип вопроса (`MultichoiceQuestion`, `ShortAnswerQuestion`, …) | Миграция БД на каждый новый тип вопроса; сложные JOIN при выборке смешанного банка вопросов; неудобно для импортера.                                    |
| Хранить только агрегированную оценку попытки (без `QuizResponse`)                             | Невозможно показать ученику разбор ошибок по каждому вопросу; невозможен переграйд (например, после исправления опечатки в правильном ответе учителем). |

## Последствия

- Расширение набора типов вопросов (Этап F, после пилота) — работа в пакете `@parta5/quiz` (новая zod-схема + функция `grade`), без миграции Prisma-схемы.
- Импортёр Moodle (Этап C) мапит `question.xml` в JSON нужного типа напрямую, минуя промежуточные SQL-таблицы.
- `questionsSnapshot` увеличивает размер строки `QuizAttempt`, но гарантирует неизменность условий уже пройденного теста — принято как оправданный компромисс ради корректности (audit trail для оценивания).
- Все таблицы квиз-движка подчиняются тому же RLS-контракту, что и остальная схема — `withTenant()` обязателен во всех tRPC-процедурах Этапа B.
